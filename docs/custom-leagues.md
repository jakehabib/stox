# Custom leagues: the league file format

A **league file** is one JSON document describing a custom league — 32
franchises and, if you want, every player on them. Export one from a league you
already have, send the file to somebody, and they can import it and play the
same league. That is the whole feature: a file you hand to a person. There is
no hosted link, no gallery, nothing published anywhere.

- **Import:** `/import`
- **Export:** the same page, or **League Settings → Share This League**
- **Code:** `lib/leagueFile.ts` (format, validation, export), `lib/leagueCsv.ts`
  (the CSV authoring path), `lib/gen/league.ts` (generation),
  `app/api/league/import/route.ts`, `app/api/league/export/[id]/route.ts`,
  `app/api/league/csv/route.ts`, `app/api/league/templates/[file]/route.ts`

**If you are building a real 1,700-player league, do not hand-write the JSON.**
Author it in a spreadsheet and convert it — see §10. JSON is the transport
format; CSV is the authoring format.

---

## 1. The smallest file that works

32 team names. No players. This produces a complete, playable league — rosters,
contracts, a free agent pool, draft picks, a schedule and depth charts are all
generated by the same code that builds a from-scratch league.

```json
{
  "formatVersion": 2,
  "kind": "dynastygm.league",
  "name": "Sunday Night Beer League",
  "teams": [
    { "city": "Akron",  "nickname": "Anvils",  "abbr": "AKR", "conference": "AFC", "division": "East" },
    { "city": "Boise",  "nickname": "Bison",   "abbr": "BOI", "conference": "AFC", "division": "East" },
    { "city": "Cody",   "nickname": "Cinders", "abbr": "COD", "conference": "AFC", "division": "East" },
    { "city": "Dover",  "nickname": "Dredgers","abbr": "DOV", "conference": "AFC", "division": "East" }
  ]
}
```

…then 28 more team objects in the same array, four in each of the remaining
seven divisions. (JSON has no comments — do not paste one into your file.)

Omit `conferences` and `divisions` and the eight divisions are `AFC
East/North/South/West` and `NFC East/North/South/West`. **Each one must hold
exactly four teams.** That is not a stylistic rule: the schedule builder
(`lib/schedule.ts`) plays weeks 1–6 as a double round robin inside each division
and skips any division that does not hold four teams, so any other arrangement
produces a season with missing weeks.

### Your own conference and division names

From format version 2 the labels are yours. The **shape** is still fixed —
2 conferences × 4 divisions × 4 teams = 32, for the reason above — but what the
two conferences and the four divisions are *called* is data:

```json
{
  "formatVersion": 2,
  "kind": "dynastygm.league",
  "name": "The College Cup",
  "conferences": ["Big Ten", "SEC"],
  "divisions": ["Lakes", "Plains", "Delta", "Coast"],
  "teams": [
    { "city": "Ann Arbor", "nickname": "Wolves", "abbr": "ANN", "conference": "Big Ten", "division": "Lakes" }
  ]
}
```

Every team's `conference` must be one of the two you listed and its `division`
one of the four — it is still a whitelist, it is just a whitelist you supplied.
The names are sanitised and length-capped exactly like a nickname, and they are
what the standings, the division headers and the playoff picture then read.

## 2. A file with players

Add a `players` array to any team. Every player needs five fields —
`firstName`, `lastName`, `position`, `age`, `ovr` — and everything else is
optional and generated if you leave it out.

```json
{
  "formatVersion": 2,
  "kind": "dynastygm.league",
  "name": "Sunday Night Beer League",
  "teams": [
    {
      "city": "Akron", "nickname": "Anvils", "abbr": "AKR",
      "conference": "AFC", "division": "East",
      "players": [
        { "firstName": "Dale", "lastName": "Wexford", "position": "QB", "age": 27, "ovr": 88,
          "potential": 92, "devTrait": "Star", "experience": 5,
          "heightIn": 76, "weightLb": 224, "college": "Cascade State",
          "attrs": { "accuracy": 91, "deepAccuracy": 86, "decision": 90, "armStrength": 88 },
          "contract": { "apy": 42000000, "years": 5, "yearsRemaining": 3 } },

        { "firstName": "Marcus", "lastName": "Oyelaran", "position": "K", "age": 31, "ovr": 74 }
      ]
    }
  ],
  "freeAgents": [
    { "firstName": "Ray", "lastName": "Tobin", "position": "WR", "age": 29, "ovr": 71 }
  ]
}
```

That second player — five fields — is entirely valid. He gets a generated body,
college, attribute spread around 74, potential, dev trait and a market-rate
contract.

## 3. Every field

### Document

| Field | Required | Notes |
|---|---|---|
| `formatVersion` | yes | Whole number. `1` or `2`. See §6. |
| `kind` | yes | Must be the literal string `"dynastygm.league"`. |
| `name` | no | League name, ≤ 60 characters. The import form can override it. |
| `conferences` | no (v2) | Exactly 2 names, ≤ 24 characters each, distinct. Defaults to `["AFC","NFC"]`. |
| `divisions` | no (v2) | Exactly 4 names, ≤ 24 characters each, distinct. Defaults to `["East","North","South","West"]`. |
| `teams` | yes | Exactly 32. |
| `freeAgents` | no | Up to 400. Omit and a 140-man pool is generated. |
| `draftClasses` | no (v2) | Exactly 1 class, up to 400 prospects. Omit and the opening class is generated. See §4a. |
| `generatedAt`, `generator` | no | Written by the exporter. Never read back. |

A file that declares `"formatVersion": 1` and then uses `conferences`,
`divisions` or `draftClasses` is **refused by name**, rather than loading here
and failing confusingly on an older build.

### Team

| Field | Required | Rule |
|---|---|---|
| `city` | yes | ≤ 24 characters |
| `nickname` | yes | ≤ 24 characters |
| `abbr` | yes | 2–4 characters, `A-Z` and `0-9` only, unique across the file. Lower case is upper-cased for you. |
| `conference` | yes | One of the file's own `conferences` (case-insensitive) |
| `division` | yes | One of the file's own `divisions` (case-insensitive) |
| `players` | no | Up to 53 |

### Player

| Field | Required | Rule | If you omit it |
|---|---|---|---|
| `firstName` | yes | ≤ 24 characters | — |
| `lastName` | yes | ≤ 24 characters | — |
| `position` | yes | One of `QB RB WR TE LT LG C RG RT EDGE DT LB CB S K P` | — |
| `age` | yes | 18–45 | — |
| `ovr` | yes | 1–99 | — |
| `experience` | no | 0–25, and never more than `age - 18` | `age - 22`, floored at 0 |
| `potential` | no | 1–99, raised to `ovr` if it sits below it | rolled from `ovr` and age |
| `devTrait` | no | `Slow`, `Normal`, `Star`, `Superstar` | rolled |
| `heightIn` | no | 60–90 | rolled from the position's body template |
| `weightLb` | no | 140–400 | ditto |
| `college` | no | ≤ 32 characters | picked from the fictional college list |
| `attrs` | no | See below | generated around `ovr` |
| `contract` | no | See below | priced at market value |

### `attrs`

An object of `attributeKey: 1..99`. The attribute catalogue is in
`lib/ratings.ts` — `speed`, `strength`, `awareness`, `accuracy`, `passBlock`,
`coverage` and so on. You may supply **as few as you like**; anything you leave
out is generated. Keys that do not apply to the player's position, and keys this
build does not recognise, are ignored rather than refused, so a file written
against a future version still loads.

**Whatever you supply, the stored overall is recomputed from the attributes.**
If you write `"ovr": 99` and then give a quarterback an `accuracy` of 40, he
will not be a 99 — the game shows the rating its own formula produces from the
attributes it actually has, because a stored overall that disagrees with the
attributes under it is a lie the rest of the app would repeat everywhere. If
you want a specific overall, give `ovr` and omit `attrs`.

### `contract`

| Field | Rule |
|---|---|
| `apy` | Average per year in whole dollars, $500,000–$100,000,000 |
| `years` | 1–7 |
| `yearsRemaining` | 1–`years`. Defaults to `years` (a deal just signed). |

Contracts are still **scaled to fit the salary cap**. If a team's total payroll
comes out above about 88% of the cap, every contract on that team is scaled
down proportionally — the same thing that happens to a randomly generated
league that rolls too many stars. A file is free to say a quarterback is worth
$80M; it is not free to hand a team a payroll the league cannot advance out of
preseason with. If keeping your exact numbers matters more than realism, spread
the money out so the team totals under ~$224M.

## 4. What import fills in, and what it leaves alone

| The file says | You get |
|---|---|
| A team with no `players` (or an empty array) | A full generated roster — the same `generateRoster` call a new league makes |
| A team with some players | **Every one of them**, plus generated players only where a position is below its roster minimum (a team with no punter cannot produce a depth chart) |
| A team with a complete roster | Exactly those players. Nothing is added. |
| No `freeAgents` | A generated pool of 140 |
| Some `freeAgents` | Those, topped up to 60 so free agency is not dead on day one |

Import **never pads a roster to a round number.** A file with 41 players per
team produces teams of 41. The app's own generated leagues sit in the low
forties anyway, and an earlier version of this that padded to 46 quietly grew a
round-tripped league by 100 players it never had.

Two players with the same name in one file: the second gets a generational
suffix (`Marcus Whitfield Jr.`), because the app guarantees unique names
league-wide and contracts are matched to players by name.

## 4a. Draft classes

A version 2 file may describe the college class the league opens with. A
prospect is a player row with a `college` and, optionally, combine numbers.

```json
"draftClasses": [
  {
    "year": 2026,
    "strength": 4,
    "players": [
      { "firstName": "Marcus", "lastName": "Doyle", "position": "CB", "age": 21, "ovr": 84,
        "college": "Ohio State",
        "combine": { "venue": "COMBINE", "fortyYard": 4.31, "vertical": 40, "benchReps": null } }
    ]
  }
]
```

**`year` is a label.** The class is stamped with the *importing* league's season
year, because `Player.draftYear` keys a class against the calendar of the league
it ends up in — a file authored for 2026 and imported in 2028 still has to be
the class the 2028 board picks from. Derived, not authored, in the same sense as
`yearsRemaining`.

**The class is topped up to 400.** Seven rounds of thirty-two picks have to find
somebody to call, so a file naming twelve prospects gets those twelve plus 388
generated ones — the same top-up rule a partial roster gets. A file naming all
400 generates nobody.

**`strength` moves the generated men and nothing else.** It is added to every
position group's own rolled bias through the one class-strength mechanism the
generator uses (`generateClassStrength`). A prospect whose `ovr` the file states
keeps it, for the same reason a rostered player does — so a *fully* authored
class has nothing for `strength` to act on, and that class publishes no
class-strength outlook rather than one describing numbers that were never
applied.

**Combine numbers do not become a rank.** Every drill is optional. The import
rolls the prospect his full six-drill battery through the same derivation every
generated prospect goes through — at his own percentile within his own position
group in this class — and then overlays whichever drills you wrote, exactly as
`attrs` overlays a generated attribute map. The **Athletic Rank** the draft board
and the player card print is computed from the *stored* six numbers at read time,
by the one function both screens call (`classAthleticRanks`,
`lib/combineRank.ts`). There is no stored rank, so there is nothing for the rank
to disagree with: an authored 4.31 is ranked as a 4.31 among whatever the rest of
the class ran. A class with no testing on file at all gets **no** rank — the
column is absent, not blank.

`benchReps: null` is "he did not lift", which six positions do and which is not
the same as lifting nothing. Omitting the field instead lets the derivation roll
him one.

`combine` is only legal inside a `draftClasses` entry. On a veteran it is
refused by name, because nothing in the app shows testing for a man who is not
in a draft class and a field that silently does nothing is worse than no field.

## 5. What export puts in the file

Export writes the current teams, the players on them, the free agent pool, and
each rostered player's contract. It deliberately does **not** write:

- ids, the schedule, standings, results, statistics
- scouting reports, the draft board, draft picks, trade history
- league history, records, the Ring of Honor
- your settings

A league file is a **starting point, not a save game**. Export a league in week
12 and the file gives whoever imports it those franchises and those players in a
fresh preseason — which is what people actually want when they say "play my
league". It is also why an export is small enough to email.

Two things are lossy and worth knowing about:

- **The free agent pool is capped at 400 on the way out.** A league that has
  been played for a while can accumulate more than that; the surplus is not in
  the file.
- **Contract money can drift by up to $100,000 per year** across a round trip.
  Contracts are stored as a schedule of base salaries rounded to $100K, the file
  carries the average-per-year that schedule implies, and rebuilding the
  schedule from that average rounds again. Length and years remaining are exact.
  Measured on a real round trip: 1,230 of 1,374 contracts identical to the
  dollar, 144 within $200K/year.

**Crests and colours do not survive a round trip.** A team's crest — its colour
pair, shape and pattern — is derived from the team's database id
(`lib/gen/teamLogo.ts`), and an imported team is a new row with a new id, so it
gets a different crest. The same is true of player avatars. The teams, the
names, the divisions and the players are identical; the colours are not. Making
them identical would mean either storing the crest on the team row (a schema
change) or reusing the exporter's ids (which collide the moment two people
import the same file into one database). Neither was worth doing for the beta —
see "Follow-ups" below.

## 6. Versioning

`formatVersion` is the first field in the document and the first thing checked.

- **This build reads versions 1 and 2 and refuses every other number, in both
  directions**, with a message naming the file's version and the build's.
- **Adding a new optional field does not bump the version.** An old reader
  ignores fields it does not know, which is exactly what you want when someone
  is on last month's deploy.
- **Removing a field, renaming one, or changing what an existing one means bumps
  the version**, and `lib/leagueFile.ts` then grows an explicit upgrade step
  from the older shape — one function, not `if (version === 1)` sprinkled
  through the validators.
- A file written today therefore still loads in six months. **Version 2 is the
  current format and version 1 files still import** — they need no upgrade step,
  because every version-2 addition is optional and defaults to what version 1
  meant: no `conferences` is `AFC`/`NFC`, no `divisions` is
  `East`/`North`/`South`/`West`, no `draftClasses` is the generated class a
  league has always had. A version 2 file on an older build is refused with
  *"written by a newer version of Dynasty GM — update the app, or ask for a
  version 1 export"*, which is a thing the person can act on. That refusal is
  the entire reason version 2 bumped the number: the conference and division
  fields went from closed enums to free strings, and an old reader has to say so
  in one sentence rather than in eight "must be one of AFC, NFC" errors.

## 7. Limits, and what happens when you exceed them

Everything below is enforced server-side in `lib/leagueFile.ts`. The browser
does a couple of the same checks first purely so you are not kept waiting; none
of them are the real gate.

| Limit | Value |
|---|---|
| File size | 8 MB |
| Teams | exactly 32, four per division |
| Conference / division names | 2 and 4, ≤ 24 characters each |
| Players per team | 53 |
| Free agents | 400 |
| Draft classes | 1, up to 400 prospects |
| Class `strength` | −12 to +12 |
| Attributes per player | 64 |
| Leagues per person | 8 (shared with normal league creation) |

**Out of range is refused, not quietly clamped.** A rating of 9999 is not a 99
you meant; it is a file that is wrong, and repairing it silently would hand you
back a league that does not match what you wrote while telling you nothing.
Every refusal names the field and its position in the document:

```
teams[7].players[3].age is 900; it must be between 18 and 45.
teams[0].players[0].contract.apy is 9000000000000; it must be between 500000 and 100000000.
teams[5].abbr "AKR" is already used by teams[0]. Every abbreviation must be unique.
Every division must hold exactly 4 teams, and 2 do not: AFC East has 3 (BOI, COD, DOV); AFC West has 5 (...).
```

The exceptions — values that are **derived** rather than authored — are clamped
instead, and there are only three: `yearsRemaining` cannot exceed `years`,
`potential` cannot sit below `ovr`, and `experience` cannot exceed `age - 18`.

**Names are cleaned, not refused.** Team and player names may contain letters
and digits in any script plus `' . - & /` and spaces. Anything else — markup,
emoji, control characters, bidi overrides, zero-width joiners — is stripped, and
a name with nothing left after cleaning is refused by name. `Café Ströms-Vik`
and `O'Malley & Sons/Co.` survive intact; `<script>Boom</script>` becomes
`scriptBoom/script`. Note that this is not the cross-site-scripting defence —
React escapes every interpolated string, so a script tag in a nickname has
always rendered as literal text. It is a **layout** defence: it stops a name
scrambling a table row or running to four thousand characters.

**Nothing is half-written.** League creation is not transactional (see
`docs/deployment.md`), so import takes the other route: it holds the id of the
league from the moment the row exists and deletes it if any later step throws.
Every dependent table cascades from `League`, so one delete removes the whole
partial save. If an import fails you get an error and no league, never a broken
one on your list.

## 8. Not built, and why

- **Hosted share links and a public gallery.** Both need moderation and storage
  decisions nobody has made. A file you hand to a person needs neither.
- **Custom colours in the format.** There is nowhere to put them without a
  schema column (see §5). Rather than accept a `colors` field and silently
  ignore it, the format does not have one.
- **More than one draft class.** The format's `draftClasses` is an array and the
  limit is 1, which is not an oversight. The app decides which class is on the
  clock by taking the newest `draftYear` still flagged `isDraftee`
  (`liveDraftClassYear`, `lib/draft.ts`), so a second class supplied up front
  would take over the draft board a year early. Next year's class is generated
  at the start of next preseason, as it always was. When the engine can hold
  more than one, the change is `FILE_LIMITS.MAX_DRAFT_CLASSES` and not the
  format.
- **Custom staff, scouts, GM personalities, draft picks, league history or
  settings.** All generated. Every one of them is more surface to validate for
  something nobody has asked for yet.
- **Roster sizes above 53 or leagues of a size other than 32.** The scheduler
  cannot produce a valid season from either.
- **Importing a save in progress** — schedule, standings, statistics, scouting.
  That is a different feature (a save file) with a much larger validation
  surface, and it is not what "share my custom league" means.

## 8a. Authoring in a spreadsheet (CSV)

Hand-writing 1,700 players as JSON is a 40,000-line document that one missing
comma destroys, and the parse error points at a line number nobody can place.
The tool people actually have is a spreadsheet, and the thing a spreadsheet does
that nothing else here does is **collaborate**: thirty-two teams split across
eight people in one shared sheet, four teams each, nothing to merge.

So **CSV is the authoring format and JSON is still the transport format.**

1. Download the templates from `/import` — `teams.csv`, `players.csv`,
   `prospects.csv`. They are generated from the code (`lib/leagueCsv.ts`), so a
   template can never offer a column the parser does not accept. `teams.csv`
   arrives filled in with thirty-two franchises; rename the cities, or rename
   the conference and division columns too and the whole league moves with them.
2. Fill them in.
3. Upload them to the converter on the same page. It hands back the league file.
4. Import that file the normal way.

The converter writes nothing. It shapes the rows into a league file document and
hands that document to `parseLeagueFile` — the same and only validator an
uploaded JSON file goes through. There is no second set of bounds to drift.

### A complete league is six columns

There are 36 attributes across 16 positions in this game and **an author does
not need them.** Set `ovr`, leave every attribute column empty, and the
attributes are generated around that overall by the same call a from-scratch
league uses. A cap-realistic 32-team league is:

```
team,name,position,age,ovr,contractApy,contractYears
BOS,Marcus Whitfield,QB,27,88,41000000,5
BOS,Dale Hersey,RB,24,76,1100000,3
```

times 1,700 rows. Attribute authorship is an optional refinement for the forty
or fifty players anybody actually has an opinion about — add a `speed` column and
fill it in for those rows only.

**And when attributes are supplied, `ovr` is ignored.** The overall is recomputed
from the attributes, because a stored overall that disagrees with the attributes
under it is the one kind of number this game will not show you. A row with
attributes *and* an `ovr` is not a conflict to resolve; the attributes are the
answer.

### The columns

- **teams.csv** — `city`, `nickname`, `abbr`, `conference`, `division`. The
  distinct values in the conference and division columns become the file's
  `conferences` and `divisions`, so naming your own needs no extra step.
- **players.csv** — `team` (an `abbr` from teams.csv, or empty for a free
  agent), `name` (or `firstName` + `lastName`), `position`, `age`, `ovr`, then
  the optional `contractApy`, `contractYears`, `contractYearsRemaining`,
  `experience`, `heightIn`, `weightLb`, `college`, `potential`, `devTrait`, and
  any attribute key as its own column.
- **prospects.csv** — the same minus `team` and the contract, plus
  `combineVenue`, `forty`, `vertical`, `broad`, `threeCone`, `shuttle`, `bench`.
  `bench` may be `none`.

Money is in dollars: `12500000`, `$12,500,000` and `$12.5M` are the same number.
A bare `12.5` is twelve dollars fifty and is refused as such, with the fix in the
message — guessing would mean a contract whose value is not the value you wrote.

### Refusals name the row

A document path is no use to a spreadsheet author, so the converter keeps a map
from every path it writes back to the row that wrote it and rewrites the refusal:

```
players.csv row 418, Marcus Doyle: position is "FB"; it must be one of: QB, RB, WR, TE, LT, LG, C, RG, RT, EDGE, DT, LB, CB, S, K, P.
players.csv row 2, Old Man: age is 900; it must be between 18 and 45.
players.csv row 2: team is "ZZZ", which is not one of the 32 abbreviations in teams.csv.
players.csv has a column called "ovrl", which is not one of its columns.
```

**A misspelled column is a refusal, not a shrug.** A column called `ovrl` that
was quietly ignored would produce 1,700 players whose overall was generated at
random, and an author who thinks they wrote a league. That is the worst outcome
available on this path, because nothing anywhere would say so.

## 9. Moderation

Team and player names are user-supplied text. For this beta that is bounded by
a length cap, a character allowlist, and a stated expectation on the import page
("please keep team and player names to things you would put on a jersey"). There
is **no word filter**, and there is deliberately no surface that publishes an
imported name to anyone who did not already choose to open the file — no
gallery, no share link, no leaderboard entry sourced from a file. If any public
sharing surface is ever added, a filter stops being optional, because
"somebody named a team something vile and it is on a public page" becomes
reachable the moment such a page exists.

## 10. Follow-ups

1. **Crest and colour fidelity.** A nullable `Team.crestSeed` column, defaulting
   to the team id, plus a `colors` / `crest` field in the format. Every
   `TeamLogo` call site would pass the seed instead of `team.id`. Roughly forty
   call sites, one migration, and it makes a shared league look identical for
   everyone.
2. **Hosted share links**, if and only if moderation is decided first.
3. **Wire the same `onLeagueCreated` cleanup into the normal create paths.**
   `createLeague` now supports it and import uses it; `createLeagueAction` and
   `/api/league/create` still leave debris on a timeout. It is six lines each.
4. **A "verify this file" endpoint** that runs the validator and returns the
   errors without creating anything, so someone hand-writing a 32-team file can
   iterate without spending a league slot per attempt.
