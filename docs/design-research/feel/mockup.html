What this page is. Five proposals from proposals.md, running. Everything is the real palette and the real component shapes. Three rules held throughout: animation never gates input (every button stays clickable while anything is animating), animation never delays information (final numbers are on screen at frame one — nothing counts up), and reduced motion loses the motion, never the information. Flip the toggle top-right and run every demo again — the same facts arrive, they just stop moving.

Proposal 4
The scouting reveal
Anticipation0 ms added to info

The scouted range (ScoutingRange.tsx) is the best anticipation object already in this codebase and today it resolves as a re-render — the bar simply is narrower. Here the band sweeps inward and newly-locked attributes land on a 60 ms stagger. The numbers are legible the entire time — we animate the transition to the answer, never the arrival of it. That distinction is the whole ethical difference between this and a loot box: no suspense pause, no near-miss framing, no rarity ceremony, no shuffled reveal order.

Zero new server work. scoutPlayerAction already returns { confidence, confidenceGained, revealed[], devTrait, remaining }. The client already holds the before (its props) and the after (the result). Everything above is presentation over data that is already in hand.

The 100 ms causality problem. The server response can be 300 ms away, and NN/g's rule is that an effect must begin within 100 ms of the action or it stops reading as caused by it. That is why the button enters its working state instantly — the pending state is not politeness, it is what makes the later reveal read as consequence.

Reduced motion: the band jumps, and the attributes all appear at once with a colour flash instead of a stagger. Try it.

Proposal 5
Live negotiation feel
The one real-time surfaceNo server calls

NegotiationPanel is the only place in this game that meets Swink's real-time control criterion — evaluateOffer is pure and client-side, so the meter reads back in well under 100 ms. It is the most game-like thing in the product and it is under-dressed. Drag the salary: threshold crossings now flare (45 / 68 / 82, the real thresholds from lib/negotiation.ts), the verdict crossfades instead of swapping, and the fill carries a linear() spring — the one place overshoot is right, because it is a control you are physically dragging. Then submit a lowball and watch a patience pip drain: dragging is free, submitting is not, and that cost should be felt.

Do not add a server call here. The file's own header explains why the whole context is resolved server-side up front: a version that posted each change would lag by a request per pixel and the entire feel would be lost. This proposal is CSS plus one ref for the previous verdict.

Why the spring is allowed here and nowhere else. Overshoot reads as physical resistance on a thing you are dragging. On a cap figure it reads as the number being wrong for 80 ms. One surface, by exception.

Reduced motion: the meter snaps, the flare becomes a static colour change, the pip empties instantly. The patience cost is still unmistakable.

Proposal 6
Dynasty level-up
Fires once per levelUnfarmable by design

lib/dynasty.ts computes XP, levels and a three-branch skill tree, and levelling up currently produces a longer bar the next time you happen to open the page. This is the app's Activity-Rings moment: celebrate exactly one thing, rarely, and stay silent otherwise. It is ethically clean to make it loud for a specific reason — the file's own header states XP is derived from real franchise results, never stored, so "there is no '+5 XP for clicking Scout' to grind." No compulsion loop means there is nothing for a celebration to reinforce.

What I am not proposing: endowed progress. The research is real — a 10-stamp card with 2 free stamps was completed by 34% vs 19% for an 8-stamp empty one — but starting a new GM at "40% of the way to level 2" is a lie about the franchise's record, and that is principle 6. Cite it, don't ship it.

Also not proposing: Duolingo-style streaks and loss aversion. This is a single-player simulator with no retention mandate. Building "don't break your streak" pressure into a game someone plays for pleasure imports a growth-team incentive into a product that has none.

Fires once per level, tracked by last-seen level in localStorage. Never on a revisit, never on every dashboard load.

The other half of the brief
Surfaces that must stay completely still
No motion, ever

This table is here to be boring, and that is the point. Hover a row: a background colour changes and nothing moves — no lift, no transition duration, no stagger, no row-enter animation. A GM edits this table dozens of times a session. It must be exactly as fast on the fiftieth edit as on the first. The same rule covers the depth chart, standings, stats, the box score, the 300-row draft board, and every sort, filter and search in the application — those are instantaneous, always, because the user is hunting and latency is the enemy.

The veto rule. If an animation means an experienced player waits longer for a number, or for the next click to register, it is deleted — not tuned, deleted.

One looping animation, total. The League Wire marquee is the app's entire ambient-motion budget and it is already spent. Nothing else may loop indefinitely: no pulsing badges, no breathing cards, no shimmer skeletons, no animated gradients. A second perpetual motion source on the same page turns ambient into noise.

No route transitions. View Transitions on navigation would tax every tab switch in a data app to make it pretty. Declined.
